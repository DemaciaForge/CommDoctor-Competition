# CommDoctor 开发计划

## 项目总体目标

开发一个面向数字通信教学的主动故障诊断与交互式修复实训平台，参加第九届传智杯 AI 创新应用挑战赛。

## 核心功能描述

### 最终用户体验
1. 系统运行真实的数字通信数学模型
2. 学生接受隐藏通信故障挑战
3. 学生通过选择测量方式收集诊断证据
4. 学生判断故障原因并尝试修复
5. 软件真实计算修复前后的通信性能
6. 系统记录诊断过程并提供教学反馈

### 技术架构概要
- **仿真内核：** 基于 NumPy/SciPy 的数字通信模型
- **故障系统：** 可配置、可注入、可观察的故障模块
- **诊断引擎：** 测量工具集、证据收集、性能评估
- **交互界面：** Web 前端（Flask/FastAPI + React/Vue）
- **教学系统：** 挑战管理、过程记录、反馈生成

### 阶段 02：实现真实、可观察、可修复的通信故障

**目标：** 设计并实现多种通信故障模型

**故障类型（初步）：**
1. **频率偏移（Frequency Offset）**
   - 物理原因：载波频率不匹配
   - 可观察：星座图旋转、解调错误增加
   - 修复方法：频率估计与补偿

2. **相位偏移（Phase Offset）**
   - 物理原因：载波相位不同步
   - 可观察：星座图整体旋转、固定错误模式
   - 修复方法：相位估计与纠正

3. **定时偏移（Timing Offset）**
   - 物理原因：采样时刻不准确
   - 可观察：眼图闭合、误码率升高
   - 修复方法：定时恢复

4. **信噪比降低（SNR Degradation）**
   - 物理原因：噪声增大或信号衰减
   - 可观察：星座点分散、误码率升高
   - 修复方法：提高发射功率或改善链路

5. **符号间干扰（ISI）**
   - 物理原因：多径传播或滤波器失配
   - 可观察：眼图闭合、波形失真
   - 修复方法：均衡器

## 风险与应对

### 技术风险
- **风险：** 通信原理理解不足导致实现错误
- **应对：** 每个模块都参考教材和论文，进行理论验证

### 时间风险
- **风险：** 个人开发，时间不足
- **应对：** 优先保证核心功能（阶段 01-04），Web 界面可简化

### 范围风险
- **风险：** 功能过多导致项目失控
- **应对：** 严格控制故障类型数量（初期只做 3-4 种）

### 竞赛风险
- **风险：** 评审标准不明确
- **应对：** 保持技术深度和完整的开发记录，而非追求表面炫技
